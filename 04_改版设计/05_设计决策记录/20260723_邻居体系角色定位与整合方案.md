## 一、核心决策：邻居 ≠ 全局陪伴，仅作情境化工具

### 1.1 角色层级定义

**主IP（3个）= 全局陪伴者**
- 吉塔（Gita）、小星（Little Star）、罗素（Russell）
- 特征：
  - 全局可达（右下角悬浮球，任何页面都能唤出）
  - 有对话能力（支持AI对话）
  - 有记忆机制（记得上次聊了什么）
  - 持续陪伴（用户主动选择的陪伴对象）

**邻居（6个）= 情境化情绪工具**
- 鸭梨（压力）、阿眠（睡眠问题）、小刺（防御/敏感）、拖拖（拖延）、小炎（愤怒）、皮皮（逃避/玩心重）
- 特征：
  - **仅在特定功能节点出现**（不占据持久化UI位置）
  - **无对话能力**（仅作情绪共鸣符号）
  - **无全局入口**（不与主IP争夺陪伴角色）
  - **故事性体现在功能场景中**（通过推荐文案、归属提示等传递人格）

### 1.2 为什么这样设计？

**问题溯源**：
- 初版方案提议在首页顶部状态条放置邻居形象 → 用户质疑："会不会和主IP打架？全局陪伴的难道不是主IP吗？"
- 如果邻居占据持久化UI位置，会模糊产品的陪伴角色层级，用户会困惑"谁才是我的AI伙伴"

**设计原则**：
- 全局陪伴权 = 主IP专属，这是产品核心价值
- 邻居 = 情绪识别和共鸣的辅助符号，丰富产品人格和故事性，但不抢主角戏份
- 情境化出现 = 在用户需要情绪共鸣的节点短暂露面，完成使命后退场

## 二、邻居整合方案：3个出现节点

### 2.1 节点1：心情打卡确认环节

**当前流程**（现有产品）：
1. 用户选择情绪（😊开心 / 😐毫无波澜 / 😔不开心 / 😤很不开心）
2. 用户选择原因（考试/同学/老师/父母/兄弟姐妹/亲人/爷爷奶奶/作业/睡眠/饮食/身体/其他）
3. 直接生成日记："今天我过得[emotion]，因为[reason]"
4. 显示连续打卡日历（5天连续有奖励）

**修正后流程**：
1. 用户选择情绪
2. 用户选择原因
3. **新增：邻居确认页**（停顿0.5秒）
   - 显示邻居头像（128×128 Q版插画）
   - 显示文案：「鸭梨：压力山大」（根据情绪+原因匹配邻居）
   - 按钮：「继续记录」
4. 生成日记 + 显示连续打卡日历

**匹配逻辑示例**：
- 不开心 + 考试 → 鸭梨（压力）
- 不开心 + 睡眠 → 阿眠（睡眠问题）
- 很不开心 + 同学 → 小刺（防御/敏感）
- 毫无波澜 + 作业 → 拖拖（拖延）
- 很不开心 + 父母 → 小炎（愤怒）
- 开心 + 其他 → 皮皮（玩心重）

**资源需求**：
- 6个邻居头像插画（128×128，Q版，统一风格）
- 匹配规则表（情绪×原因 → 邻居 + 文案）

### 2.2 节点2：脑之岛推荐卡

**触发条件**：
- 过去5天内，某个邻居在心情打卡中出现 ≥3次
- 每日刷新推荐逻辑

**显示位置**：
- 首页主Feed流第2-3屏（首屏下方，不占据首屏核心区域）

**显示内容**：
- 邻居头像（128×128）
- 推荐文案：「小刺最近常来找你，试试正念冥想？」
- 训练卡片入口（点击直接跳转到对应脑之岛训练）

**推荐逻辑示例**：
- 鸭梨（压力）频繁出现 → 推荐「放松训练」或「呼吸练习」
- 阿眠（睡眠）频繁出现 → 推荐「睡眠冥想」
- 小刺（防御）频繁出现 → 推荐「正念冥想」
- 拖拖（拖延）频繁出现 → 推荐「时间管理训练」
- 小炎（愤怒）频繁出现 → 推荐「情绪管理」
- 皮皮（逃避）频繁出现 → 推荐「勇气挑战」

**设计意图**：
- 将邻居体系与脑之岛训练系统打通
- 用户看到"小刺最近常来"，会意识到"我最近确实容易防御"
- 推荐训练时，不是冷冰冰的"建议你做XX训练"，而是"小刺陪你一起面对"

### 2.3 节点3：解忧信箱归属提示

**触发时机**：
- 用户在解忧信箱提交烦恼后，底部toast提示（2秒后消失）

**显示内容**：
- 邻居头像（小图标，48×48）
- 文案：「阿眠看到了你的困扰，我们一起面对」

**匹配逻辑示例**：
- 烦恼内容含"睡不着/失眠" → 阿眠
- 烦恼内容含"压力/考试/作业" → 鸭梨
- 烦恼内容含"同学/被排挤/孤立" → 小刺
- 烦恼内容含"拖延/不想做" → 拖拖
- 烦恼内容含"生气/愤怒/吵架" → 小炎
- 烦恼内容含"不想面对/逃避" → 皮皮

**设计意图**：
- 给解忧信箱一个"有人看到"的归属感
- 用户不是把烦恼扔进黑洞，而是"阿眠接住了我的困扰"
- 为后续可能的邻居主题信箱回复预留设计空间

## 三、邻居体系不出现的位置（明确边界）

### 3.1 首页顶部状态条
- **现状**：年级切换 + 积分显示
- **不添加**：邻居形象或emoji
- **原因**：顶部是持久化UI，邻居不应占据全局位置

### 3.2 全局导航/底部Tab栏
- **现状**：首页/脑之岛/解忧信箱/我的
- **不添加**：邻居入口
- **原因**：导航是功能划分，邻居不是功能模块

### 3.3 主IP悬浮球附近
- **现状**：右下角IP悬浮球（全局陪伴入口）
- **不添加**：邻居悬浮球或切换入口
- **原因**：全局陪伴 = 主IP专属，邻居不与之争夺角色

## 四、首页内容模块决策

### 4.0 已确认模块清单

| 模块 | 决策 | 备注 |
|------|------|------|
| 主IP大形象 | ✅ 必做，右侧固定列，状态联动 | 右侧独立列（约280px），不与打卡区视觉元素重复。打卡前：IP等待/问候状态；打卡后：IP换表情+说一句情绪回应。视觉锚点 + 功能意义兼顾，非纯装饰 |

## 六、决策验证标准

### 6.1 用户认知检验

**测试问题1**：打开App后，谁是你的AI伙伴？
- ✓ 正确答案：吉塔/小星/罗素（主IP）
- ✗ 错误答案：邻居（说明邻居抢了主IP的角色）

**测试问题2**：鸭梨/阿眠/小刺是做什么的？
- ✓ 正确答案：代表我的情绪状态，帮我看到我最近的心情
- ✗ 错误答案：我的聊天对象 / 我要选一个养成（说明角色混淆）

### 6.2 产品目标对齐

**目标1：丰富产品人格和故事性** ✓
- 邻居体系通过6个角色，让情绪识别更有温度
- 用户不是在"标记情绪"，而是"看到自己的心情被某个小伙伴接住了"

**目标2：不增加认知负担** ✓
- 邻居不需要用户主动选择或管理
- 自动匹配，出现即理解，退场即消失

**目标3：可扩展到其他模块** ✓
- 脑之岛推荐：邻居频次 → 训练推荐
- 解忧信箱：烦恼归属 → 邻居共鸣
- 未来可扩展：邻居主题回信、邻居成长故事等

**目标4：不与主IP角色冲突** ✓
- 邻居仅情境化出现，不占据全局陪伴位置
- 主IP保持唯一的全局陪伴者角色

## 七、决策依据与参考

### 7.1 用户反馈原话

**问题1**：
> "邻居只展示emoji的话，还需要文案去解释它对应的是什么心情，这个识别性比😊表情状态更难懂，而且只用邻居动物emoji的话，怎么能让这个邻居形象的故事关在其他功能板块有所体现呢？"

**回应**：
- 放弃emoji-only方案
- 改用128×128头像插画 + 文案组合
- 在脑之岛推荐、解忧信箱归属等场景扩展邻居故事

**问题2**：
> "首页顶部小状态条里出现邻居的形象，会不会和主IP打架？全局陪伴的难道不是主IP吗？"

**回应**：
- 明确角色层级：主IP = 全局陪伴，邻居 = 情境化工具
- 邻居不出现在顶部状态条、导航栏等持久化UI位置
- 仅在心情打卡、推荐卡、归属提示等特定节点短暂露面

### 7.2 设计原则依据

**原则1：为后续构架打好框架**（用户明确要求）
> "我不想做无用功，不是为了跑闭环1而做，是真正能为后续的构架打好首页的框架"

**回应**：
- 采用D2功能版作为基座（已验证的3.5-4分水平）
- 精准修正邻居整合方式，而非推倒重来
- 建立可扩展的邻居匹配规则体系

**原则2：情境化出现 > 持久化展示**
- 参考Headspace的意图驱动导航：功能在需要时出现，不需要时隐藏
- 邻居不是"功能模块"，而是"情绪共鸣的瞬间"
